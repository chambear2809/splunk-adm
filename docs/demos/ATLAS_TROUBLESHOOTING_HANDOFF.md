# Application Atlas troubleshooting lab handoff

**Copy this entire document into a new chat in the `splunk-adm` workspace.** Use it as the execution brief. The mission is to demonstrate how an operator uses Project Atlas to follow a real connection, locate the first broken or unobservable segment, identify the likely cause, and verify recovery.

## Objective and deliverables

Build a thorough, screenshot-led **troubleshooting walkthrough of this validation lab**. The lead story should start at a real client and trace one real traffic conversation end to end, then work through its return path. Follow with the minimum number of distinct journeys needed to cover the lab's remaining forwarding points. For each journey, show how to start in Atlas, what to look at, and what decision the evidence supports.

Deliver:

1. A **lab topology and coverage map** that locates every confirmed forwarding point, alternate path, attachment, workload and observation source. Show separately which devices are traversed, which are evidence providers, and which are management or collection systems.
2. A **scenario ledger** with a record for every scenario below and for any additional scenario discovered in preflight. Record routing scope, prerequisites, assets and hops exercised, test/control, Atlas view or explicit readiness gap, evidence, and recovery. Keep detailed operator evidence protected.
3. A **self-contained shareable HTML walkthrough** at `docs/demos/atlas-validation-scenarios.html`, or a new candidate alongside it until verified. Use embedded screenshots, concise captions and expandable per-hop detail. Lead with the best native Atlas investigation. Use supporting Splunk or device evidence where it helps explain the story. Only include demonstrated results and clearly identified limitations. Preserve existing user edits and verified captures.
4. An execution summary with the link to the HTML, demonstrated coverage, remaining collection or product gaps, and the exact dependency blocking any incomplete scenario. Keep candidate ideas and failed qualification attempts in the ledger.

This is a lab troubleshooting exercise. Work only with authorized lab devices, benign requests, scoped defensive tests and approved access. Leave unrelated systems and existing workloads undisturbed. Continue safe independent work when a prerequisite is blocked. Ask only when you need access, a material scope decision, or approval for a disruptive operation that the existing authorization does not cover. Do not send, publish or push artifacts without instruction.

- A previous scoped FTD deny and rollback matched client outcomes, Hubble, the rule counter and timed Nexus cache reads. Another test matched app3 to the HAProxy DB frontend, HAProxy's distinct backend connection to PostgreSQL, and the tagged read-only TLS session on the primary. Use these receipts to choose fresh repeatable tests.

Native Impact asked for a mapped routing scope. Background jobs were disabled. The supplied vCenter did not expose the Splunk VM. Recheck all of these states and record the evidence date.

## Execution order

**1. Inventory the path and observation points.** Confirm environment identity, device role and reachability, active ports and neighbors, VLAN/VRF/VNI where relevant, fabric and gateway attachments, FTD inside/outside interfaces and management relationship, ESXi host/uplink/vDS/dvPort/port group and VM vNIC, pod/node/service/EndpointSlice, VIPs and actual backends. Use read-only device and workload checks first. Draw directional candidate paths from verified topology. Maintain one coverage row per accessible device or meaningful boundary, including unused alternatives and reasons. A single flow may take only one ECMP member, stay on a vDS, skip the firewall, or use a different return route. Choose distinct real journeys to cover those branches.

**2. Qualify native Atlas on the lead flow first.** Reuse the known K3s-to-Splunk path as the first canary, or select an equally well-understood sanctioned listener. Prove producer → transport and template decode → searchable native sourcetype → observation identity and correct routing scope → time-bounded identity/attachment → Trace/Device/Map read → restricted viewer. Verify actual raw receipt and the macro output on the same test flow before relying on screenshots. Where native rendering is blocked, isolate the exact pipeline stage. Keep CLI, inventory and packet evidence available for comparison. Avoid turning old snapshots or converted device-cache rows into claims of continuous vendor ingestion.

**3. Close the telemetry gaps in dependency order.** Use the current deployment and operator contracts. An isolated collector or disposable source can prove transport before touching a shared exporter. Preserve existing exporters and their receivers. If a change to collection is in scope, record exact ownership, preflight, narrow target, rollback and verification. Verify auth, TLS, retention and least-privilege viewer access. Recheck the effective app namespace, routing mappings and raw/derived access before enabling any writer. Keep a control channel reachable throughout any controlled incident. Stop a change and recover if it affects an unrelated destination, a shared health check or the operator's access path.

**4. Run the scenario matrix.** Prioritize A first, then B and C. Check every D prerequisite and execute the supported cases. Add newly discovered cases only when they answer a distinct operator question, exercise an uncovered path or explain a material evidence boundary. Parallelize read-only analysis and independent captures using AGENTS.md. Coordinate one owner for shared changes and the HTML. Keep executing until remaining work is specifically blocked, outside authorization or unsupported by the actual lab.

**5. Reconcile and capture.** Verify results through the existing viewer role and record when only admin access is available. Confirm the final Atlas state and all temporary rule, token, listener, workload, capture, search-job and other cleanup. Keep tests bounded and record deviations. Validate HTML offline at desktop and mobile widths, check each image, and open any viewer-only deep link where available. Keep links to authenticated lab endpoints in the operator ledger if the shareable file is for general distribution.

## Evidence and acceptance rules

### Hop ledger and correlation

For every direction and segment record `case, phase, flow_id, UTC start/end, scope, source/destination labels, protocol and ports, observer and interface, routing/translation context, evidence kind, native Atlas view, receipt reference`.

- Use absolute UTC windows and record both event and receipt timestamps where they differ. Use fixed test source ports, trace/request IDs or PostgreSQL application tags. Prefer metadata and minimize or avoid payload collection.
- Match the full tuple, window and observer. Record the before/after tuple at SNAT/DNAT. For services or load balancers, represent each transport leg and join it with independent correlation such as selected endpoint UID, HAProxy session, application request tag or DB session. Document when an observer sees only encapsulation or a sampled flow.
- Mark each hop **Observed**, **Inferred from verified topology**, or **Unverified**. A switch cache can establish traversal on its recorded ports. CDP/LLDP can establish adjacency. vCenter can establish attachment. Direction and same-flow correlation determine which evidence can be joined. Never invent a hop to fill a diagram.
- Compare a known-good control against the incident. Require exact matching for before/during/after, with rollback evidence. A timeout by itself leaves the cause open. Zero records means zero visible matches in the tested window and observer scope. Support a confirmed deny with positive verdict/counter evidence.
- Track **Native Atlas verified**, **Companion evidence only**, **Conditional or blocked**, or **Outside current lab** per scenario. A native pass needs the real view to show the expected live evidence in the selected window. Mock screens, old ACI captures, local what-if results, and data-health screenshots have their own provenance.

### Minimum native checks

| Boundary | Verify before calling the native path demonstrated |
| --- | --- |
| Cilium/Hubble | Expected cluster/namespace/pod, correct direction, tuple and UUID, event verdict/reason, receipt and observer scope. Default L3/L4 visibility does not establish HTTP content or DNS behavior. |
| Nexus/Stream | Device model and software, supported monitored interfaces, exporter/observation-domain identity, parsed template and `stream:netflow` tuple, input/output ifIndex and physical neighbor identity. Validate inner versus outer flow visibility and active/inactive cache/export timing. |
| VMware/vSphere | vNIC/dvPort/port group, host, vDS and uplink mapping for the specific window. Require device-side flow/capture or verified exporter attribution for observed traversal. Evaluate supported vDS IPFIX or scoped mirroring only on approved test resources. |
| FTD/FMC | Verify targeted managed device, connection/rule event, original and translated address/port, inside/outside direction and valid observer mapping. Qualify actual eStreamer receipt and `cisco:sfw:estreamer` parsing. FMC manages the policy and provides evidence. FTD is the forwarding point. |
| Kubernetes and traces | Verify workload UID and validity interval, Service and selected backend, real trace lineage and scope. Include observation gaps, reschedules and lifecycle where relevant. |
| Atlas and Splunk | Test exact configured indexes, scoped observer eligibility, temporal identity and attachment, native query output, view/time behavior, ACLs and retention. Check raw receipt versus derived summaries. Report the first unverified link in the chain. |

### Walkthrough format

Start each scenario with a support-ticket question and the customer-visible symptom. Use **What happened**, **What to open**, **What to look at**, and **What the evidence supports** as the authoring checklist. Include:

- An operator's click path. Start with Applications, Find or Endpoints when the operator knows a service or address. Move to Map or Trace to identify the first failed or unobservable segment, then open Device, Data Health, comparison or Impact when that view answers the next question. Verify each advertised transition against the installed release.
- An annotated forward/return path or a before/during/after comparison, with source and destination visible by shareable labels.
- A native Atlas screenshot where verified, cropped to the relevant feature and labeled with its fixed window. Show the port, verdict, health indicator, identity change, affected dependency or gap the operator should inspect.
- One short caption per screenshot. Place any essential companion evidence beside the hop it corroborates.
- An expandable per-hop timeline or table for exact ordering and qualification. Keep test labels consistent when anonymizing. Never include passwords, auth headers, private management addresses or customer records.

Acceptance is coverage of all the materially different paths this lab can demonstrate, using the fewest distinct cases that still explain each troubleshooting decision. Reconcile the inventory and scenario ledger before finishing. For every unresolved item, record the exact missing access, telemetry, feature support or change authorization and the best evidence already obtained.
