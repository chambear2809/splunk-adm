The visible inventory had five connected, powered-on hosts, one cluster reporting HA disabled, and eight datastores with free capacity. Available storage is not proof of suitable placement, compute headroom, independent failure domains or permission to use it. The inventory also included an Ubuntu-named powered-off VM and a Linux cloud-image library item; their presence does not establish that either is a usable template or an authorized resource. Host and cluster free CPU/RAM, template suitability, placement, quotas, and resource ownership remain unverified. Identify the correct vCenter and VM by independent BIOS UUID and MAC confirmation, then inspect its disks and datastore, available capacity, Tools, existing snapshots and snapshot privileges before planning changes.

A VMware snapshot is not a backup; Broadcom's [snapshot guidance](https://knowledge.broadcom.com/external/article/318825/best-practices-for-using-vmware-snapshot.html) treats it as a temporary mechanism. A crash-consistent snapshot does not establish application consistency, and a quiesced filesystem alone does not establish Splunk or KV Store consistency. Before an upgrade, establish an independently stored, restorable backup of configuration, indexed data and application state, and follow the version-specific [Splunk KV Store backup and restore procedure](https://help.splunk.com/en/splunk-enterprise/administer/admin-manual/10.6/administer-the-app-key-value-store/back-up-and-restore-kv-store), including the applicable consistency and deployment limitations. Rehearse restore on an isolated authorized target and verify data and permissions. A VM snapshot, if separately authorized and appropriate, requires identified target, sufficient datastore headroom, checked Tools/quiesce support, existing-snapshot review and a documented removal plan. No backup or restore test was performed here.
