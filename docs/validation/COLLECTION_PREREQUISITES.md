# Kubernetes collection prerequisites

Read-only inventory on 2026-11-19; this is a planning record, not a collection or upgrade approval. The destination platform upgrade remains blocked. No collector, HEC endpoint, OTLP destination, token, index, or heavy forwarder was provisioned or verified by this inventory.

## Observed sources and support boundaries

- One Ready k3s control-plane node runs Kubernetes `v1.37.2+k3s1` on Ubuntu 24.04.5 LTS, kernel 6.8, containerd 2.3.7. This single-node inventory is not high-availability evidence.
- The Cilium DaemonSet has Helm chart label `cilium-1.20.5`, release `cilium`, image `quay.io/cilium/cilium:v1.20.5` pinned by digest, and 1/1 ready. Cilium operator and Hubble relay also use 1.20.5 images; Hubble UI uses 0.13.6. Hubble and Gateway API are enabled in the observed Cilium ConfigMap. Kube-proxy replacement is enabled, routing is tunnel mode, and monitor aggregation is `medium`.
- Cilium's [1.20.5 compatibility documentation](https://docs.cilium.io/en/stable/network/kubernetes/compatibility/) lists Kubernetes 1.33–1.36 as end-to-end tested; 1.37 depends on Kubernetes backward compatibility and is not covered by that documented guarantee. The [requirements](https://docs.cilium.io/en/stable/network/kubernetes/requirements/) make the same distinction. This is an unqualified combination, not proof that it fails.
- The application operator guide describes chart 0.161.0, but no collector was identified by name in the observed pod/workload inventory, so it is a **proposed pin**, not an installed chart or confirmed image. The vendored collector workflow audits chart 0.158.0 instead, and its installation Job's Kubernetes compatibility gate covers 1.34–1.36. It does not establish 0.161.0 on 1.37. The repository manifest records the chart archive and a publisher-verified SHA-256; reverify the selected archive, determine and pin its actual images, and obtain vendor support or qualify an updated workflow before deployment. The upstream [chart source](https://github.com/signalfx/splunk-otel-collector-chart/blob/main/helm-charts/splunk-otel-collector/Chart.yaml) establishes chart identity, not this cluster combination's support.
- No Tetragon or LLDP-named pod was found. Host-level installation, tracing policies, Hubble static flow export, workload instrumentation, and their actual output are unverified. The inspected `cilium-config` did not expose the checked static-export fields; this alone cannot prove that no exporter is configured elsewhere. Hubble enablement does not establish flow-file delivery.

## Prerequisites and acceptance

1. Confirm intended cluster identity, data scope, Kubernetes/Cilium and collector support, chart and image supply chain, resource ownership, and change window. The 0.161.0 guide and 0.158.0 audited workflow have different baselines; reconcile them rather than silently overriding a gate. Validate the whole selected deployment and rollback lifecycle on a representative cluster.
2. Define the HEC or approved OTLP receiving architecture, certificate trust, protected token lifecycle, indexes, retention, event volume and network rules. Select only required signals; the vendored collector workflow treats Platform traces as experimental and requires explicit acceptance. No endpoint or credential is allocated by this record.
3. For Kubernetes object history, grant only the required `get`, `list`, and `watch` access to Pods, Services, Nodes, EndpointSlices (`discovery.k8s.io`), Ingresses (`networking.k8s.io`) and, where used, Gateways and HTTPRoutes (`gateway.networking.k8s.io`). Configure watch and `include_initial_state: true`; prove pre-existing objects appear, then prove add/update/delete and EndpointSlice backend replacement events, restart resnapshot and recovery after watch interruption. Verify permissions against the actual service account and preserve event time, cluster identity, UID and source fields. Bound object and namespace scope where supported.
4. For Hubble, review scope, field masks, privacy/redaction, rotation and file permissions; configure and verify the static export and read-only collector mount only through an approved change. Prove node coverage and representative forwarded, dropped and relevant L7 events at the destination. Medium monitor aggregation can suppress evidence; unresolved paths must stay unresolved. For runtime-security evidence separately confirm Tetragon presence, TCP connect policy, event schema and forwarding. Do not infer process-connect events from Hubble.
5. LLDP is only required for host-to-fabric attachment context; verify host installation, Kubernetes node-name alignment and switch receipt when selected. For traces, separately prove workload instrumentation, parent/child and service attributes, propagation and index arrival. Record one-hour representative samples per selected source, timestamp fidelity and expected sourcetypes; successful configuration alone is insufficient.
6. Size any heavy forwarder for the selected modular inputs and forwarding workload using measured peak events/bytes, CPU, memory, queue/disk buffering, network throughput, restart/backpressure behavior, and upstream/downstream capacity. Determine ownership, redundancy, retention, monitoring and recovery objectives; no sizing or availability is established by this inventory. Keep modular inputs on the designated heavy forwarder per [operator topology](../operators/README.md), while choosing actual HEC/OTLP routing separately.
7. Verify receipt and access in the intended destination, collector and node health, RBAC least privilege, per-source data quality, missing data and failure behavior. Preserve configurations and evidence for disable-first rollback; do not enable Atlas source selection until its target/source acceptance checks pass. See [Kubernetes operator guide](../operators/kubernetes-platform.md) and [Cilium operator guide](../operators/cilium-isovalent.md).
