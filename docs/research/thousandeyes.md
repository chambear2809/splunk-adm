## What the app collects

The app supplies six distinct evidence families. Metrics, traces, activity and alerts are four push integrations to Splunk HEC. Detected events and path visualization use API pull inputs; path visualization is attached to the metrics input.

| Family | Producer and collection | Package sourcetype | Main identity and time evidence |
| --- | --- | --- | --- |
| Test metrics | ThousandEyes OTel v2 `metric` stream to HEC. Supports CEA metric tests across network, BGP, HTTP, DNS, page load, web transaction, API, FTP, SIP and voice/RTP families. The app filters endpoint tests to agent-to-server and HTTP-server types. | `cisco:thousandeyes:metric`; source `cisco:thousandeyes:stream` | Resource identity includes `thousandeyes.account.id`, `thousandeyes.test.*`, `thousandeyes.source.agent.*`, and `thousandeyes.stream.id`; exact flattened HEC datapoint value/time field paths require a sanitized readback. |
| Path visualization | Optional API pull controlled by `related_paths`; selected tests are queried on the configured interval. The app supports CEA and endpoint scheduled/dynamic path endpoints. | `cisco:thousandeyes:path-vis` | Endpoint result schema includes `aid`, `testId`, `agentId`, `roundId`; CEA schema has `date`, `roundId`, `startTime`, `endTime`, `agent.agentId`, and path fields, but does not define per-result `aid` or `testId`. |
| Synthetic traces | ThousandEyes OTel v2 `trace` stream. ## Identity, time, and routing rules

- **Account group:** Do not assume one universal raw key. Events add `aid`; endpoint path results include `aid`; CEA path results do not document it in each result; alerts use `accountId` plus `orgId`; OTel signals use `thousandeyes.account.id`. The vendor app's dashboards rename OTel account ID to `aid` and look up `thousandeyes_account_group`, so that is the app's operational convention. The official OTel schema itself describes `thousandeyes.account.id` as an account ID without explicitly stating that it equals API `aid`. Preserve the original key and the organization ID, and canonicalize only after matching the value to `/account-groups` or a received sample.
- **Test and agent identity:** Metrics and traces carry `thousandeyes.test.id` and `thousandeyes.source.agent.id`. Alerts only carry test identity when the alert has a test. API events must be checked for test references before joining. CEA path response schema has `agent.agentId` but no per-result `testId`; the test ID is the request path parameter. Endpoint path results have `testId`, `agentId`, and `aid` in each result. Activity logs identify users and resources, not test agents.
- **Splunk metadata:** OTel metric, trace, and activity stream configuration explicitly sets source, sourcetype, and selected index. The alert template explicitly sets source, sourcetype, and index. Event/path modular-input code sets event data, stanza, and sourcetype (path) but does not explicitly set `source` or `host`; index is inherited from input configuration. Do not infer the modular-input source value without official Splunk behavior or a Splunk readback. No family sets Splunk `host` to a ThousandEyes test or agent.
- **Event time:** Every six family stanzas in `default/props.conf` specify `DATETIME_CONFIG=CURRENT`. The configured raw timestamp parser uses current time, but an explicit HEC event-metadata `time` can supply `_time` independently. Retain `_time` as unqualified row time until the actual received envelope proves its basis; use `_indextime` for indexed receipt and native signal fields for measurement time. Cisco's metrics reference does not specify the HEC datapoint time key/field path; confirm it from a readback. Traces use start/end Unix nanoseconds; activity logs carry `Timestamp` and `ObservedTimestamp`; events carry ISO date strings; alert times are epoch milliseconds. Cisco's CEA path model defines `date` as UTC ISO datetime and `roundId`, `startTime`, and `endTime` as epoch seconds; the packaged `duration=endTime-startTime` therefore yields seconds when present. Endpoint path summaries define `roundId` in seconds; endpoint detail `systemMetrics.startTimeMs` and `endTimeMs` are epoch milliseconds for the metrics-collection interval, not the path round.
- **Units:** Use the producer's unit. The official OTel metric schema documents latency/durations in seconds, jitter in milliseconds, loss/completion/availability in percent, throughput in bytes per second, BGP counts, and voice MOS/loss/discard metrics. Path `responseTime` is milliseconds; path round IDs are timestamps, not durations. Trace span duration is derived from nanosecond start/end values (the app's alias calculates milliseconds).

The package's own metric data model types `thousandeyes.account.id` and some agent IDs as numbers, while the OTel metric schema calls account/source-agent IDs strings; traces use strings. Do not coerce IDs before checking an actual HEC event and the account-group lookup values.

## CEA path identity bridge and trace qualification

The CEA path identity gap is visible in the shipped code. `bin/test_metrics_stream_input.py` lines 187–192 passes the selected test ID and account-group ID into the API request; `bin/thousandeyes_client.py` lines 493–520 places `aid` in query context and the test ID in the URL path; `bin/test_metrics_stream_input.py` lines 332–338 serializes each API result unchanged. Cisco's CEA result model does not repeat either identity. For normalized CEA path records, an external export adapter is the required bridge: attach the exact configured `aid` and selected test ID to each unchanged result. The adapter may be an optional deployment component, but CEA path cannot be admitted as typed account/test data without it or an adequate received native payload. It does not install or schedule another input in the Cisco Splunk package.

Package code `bin/thousandeyes_constant.py` lines 108–112 allow-lists `page-load`, `web-transactions`, and `api` for traces. Cisco's detailed [OTel traces reference](https://docs.thousandeyes.com/product-documentation/integration-guides/opentelemetry/data-model/data-model-v2/traces) describes API trace layers, but the general [OTel v2 signal overview](https://docs.thousandeyes.com/product-documentation/integration-guides/opentelemetry/data-model/data-model-v2) and [Splunk app input guide](https://docs.thousandeyes.com/product-documentation/integration-guides/custom-built-integrations/splunk-app/inputs) list traces for page-load and web transactions only. Treat API as package-code/config eligible but unresolved at the app producer boundary until Cisco confirms or a sanitized stream sample is received.

## Compatibility and static-analysis limits

The current Splunkbase listing says Splunk Enterprise/Cloud versions 9.1 through 10.6 and CIM 6.x. The extracted README lists 9.1 through 10.4, while Cisco's app guide currently lists 9.1 through 10.3. Treat the listing as the current release metadata, and confirm compatibility for the exact deployment before rollout. The archive declares Python 3.9 and 3.13 for its modular inputs.

This is configuration/source evidence, not proof of collection completeness. No ThousandEyes account was queried and no live HEC event was received. In particular, validate flattened HEC field names, `host` and default modular-input `source`, event timestamp handling, CEA path account/test scope, and ID types from a sanitized readback before building typed normalization around them. The detailed matrix and fixture checklist are in [ThousandEyes capabilities and schema](thousandeyes-capabilities.md).

## HEC timestamp and static vendor finding

[Splunk HEC metadata documentation](https://help.splunk.com/en/splunk-enterprise/get-started/get-data-in/10.6/get-data-with-http-event-collector/format-events-for-http-event-collector) defines an explicit event timestamp in the outer `time` field. The packaged `CURRENT` setting alone therefore does not qualify `_time` as receipt time for every received stream. Atlas preserves row, index, collection and native measurement times separately.

The supplied archive has an apparent missing closing parenthesis in `default/props.conf:45`, the trace `EVAL-response_time` expression. Atlas reads native raw fields and does not rely on that alias. The final installed qualification must record its actual effect; the vendor archive and copied search-time configuration remain unchanged.
