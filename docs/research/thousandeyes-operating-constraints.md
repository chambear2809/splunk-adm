The current Cisco integration guide's compatibility table is narrower and stale relative to that listing: it says Enterprise 9.1–10.3 and CIM 6.0.1. Treat 0.9.0 as the current package version, but retain this publisher-documentation mismatch when planning a rollout. ## Input placement, HEC, and index kind

The app has **four push** families (metrics, traces, activity logs, alerts) and **two pull** families (detected events and path visualization). Path visualization is an API pull attached to the Tests Stream - Metrics input; Cisco's input-to-source table does not list it as a separate input row. [Cisco inputs guide](https://docs.thousandeyes.com/product-documentation/integration-guides/custom-built-integrations/splunk-app/inputs)

For **this Splunk app**, Cisco requires an events index. The input guide explicitly says the test metrics, path, trace, event, activity, and alert indexes must be events indexes; it also requires HEC to be enabled and reachable from ThousandEyes, SSL enabled with a valid non-self-signed certificate, and an enabled HEC token. The HEC token's allowed indexes must include the chosen index. The app examples target `/services/collector/event`. Do not route these app inputs to a metrics index based on the separate direct-OTel guide.

The **separate direct ThousandEyes OTel-to-Splunk integration** documents both `/services/collector/event` and `/services/collector` endpoints and event or metrics indexes. Its `mstats` examples demonstrate that the direct OTel path can use a metrics index; they do not change the app 0.9.0 input guide's event-index requirement. The direct guide also says ThousandEyes cannot validate the self-signed HEC certificate used by Splunk Cloud free trials. [Direct OTel-to-Splunk guide](https://docs.thousandeyes.com/product-documentation/integration-guides/opentelemetry/observability-platforms/splunk-cloud-or-enterprise)

| Family | Cisco app guide source / sourcetype / method | Version-specific package observation |
| --- | --- | --- |
| Metrics | `cisco:thousandeyes:stream` / `cisco:thousandeyes:metric` / push | `thousandeyes_constant.py` sets HEC signal `metric`, data model v2, `/services/collector/event`, source and sourcetype. |
| Traces | `cisco:thousandeyes:stream` / `cisco:thousandeyes:trace` / push | Package config sets HEC signal `trace`, data model v2, `/services/collector/event`, source and sourcetype. Cisco app docs describe CEA page-load and web-transaction test traces; package constants also list API traces. |
| Activity logs | `cisco:thousandeyes:stream` / `cisco:thousandeyes:activity` / push | Uses the OTel stream. Cisco's input docs permit account group `All`, subject to TE permissions below. |
| Alerts | `cisco:thousandeyes:webhook` / `cisco:thousandeyes:alerts` / push | Creating the input creates a webhook operation and connector and associates the operation with selected alert rules. |
| Detected events | source `N/A` / `cisco:thousandeyes:event` / pull | A Splunk modular input calls the API and writes JSON events. |
| Path visualization | Not separately mapped in Cisco's input/source table | The package's metrics-stream input calls the test-level Path Visualization API, then writes returned result objects as `cisco:thousandeyes:path-vis`. A package constant names the path source `cisco:thousandeyes:stream`, but `ingest_path_info()` does not pass an explicit `source=` to `smi.Event`; the effective Splunk source and `host` are unverified. |

The app package sets source and sourcetype for its OTel metrics/trace stream payloads, but the input guide also asks administrators to configure a HEC token source-name override. Cisco's published mapping is therefore the expected mapping, not proof of what a deployed HEC token or producer actually wrote. The package/docs do not establish a canonical `host` value. Confirm `_raw`, `source`, `sourcetype`, `host`, `index`, and HEC wrapper metadata in a sanitized staging readback before using those values as enforced admission keys.

## Authentication and permission scope

Splunk configuration pages require `admin_all_objects` or `sc_admin_all_objects`; Cisco says the built-in `admin` and `sc_admin` roles have those permissions. ThousandEyes authorization is an OAuth device-code flow through the ThousandEyes login page. Cisco's current required permission list is: API access; edit connectors and operations; edit streaming integrations; edit alert rules; login via ThousandEyes login page; view all users; view activity log for all users in account group; view connectors and operations; view endpoint experience tests; view labels; view own activity log; view tests; view user activity in all account groups; and view alert rules. Cisco documents weekly automatic access-token refresh and says the token does not expire. The packaged OAuth scope string is `organization:read offline_access tests:read endpoint-tests:read streams:manage alerts:manage tags:read integrations:manage`; that static scope list is package evidence, not a replacement for Cisco's required TE permission list. [Cisco configuration guide](https://docs.thousandeyes.com/product-documentation/integration-guides/custom-built-integrations/splunk-app/configuration)

Collecting activity for **All** account groups requires `View user activity in all account groups`; per-group activity requires `View activity log for all users in account group` (plus the documented activity permissions). Cisco explicitly warns that alerts input setup creates/edits ThousandEyes integration resources and associates the webhook with selected alert rules. Do not treat that input as a read-only configuration action.

## Account identity and path detail

ThousandEyes v7 defines `aid` as the unique account-group ID returned by `/account-groups`; account-group responses separately expose `orgId`. Cisco's OTel v1/v2 schemas define `account.id` / `thousandeyes.account.id` only as “the ID of the account” associated with telemetry. The packaged TA aliases `thousandeyes.account.id` to `aid`, but the official OTel schema does **not** state that this OTel field is the native account-group `aid`. Keep the identity equivalence unverified until a sanitized readback or explicit Cisco confirmation. The packaged alert webhook template emits `accountId` from `alert.rule.account.id` and `orgId` from `alert.rule.account.organization.id`; it preserves these as separate fields. `props.conf` also contains a `thousandeyes_account_id` to `accountId` alias, but that key is not in the current package template. [Cisco v7 account groups API](https://developer.cisco.com/docs/thousandeyes/list-account-groups/) · [OTel v2 metrics schema](https://docs.thousandeyes.com/product-documentation/integration-guides/opentelemetry/data-model/data-model-v2/metrics) · [OTel v2 logs schema](https://docs.thousandeyes.com/product-documentation/integration-guides/opentelemetry/data-model/data-model-v2/logs)

The packaged path collector requests `/test-results/{testId}/path-vis?aid=...` and emits each returned result unchanged; it does not attach the request's `aid` or `testId` itself. The test-level response provides summary data; the separate **agent-and-round detail** response is required when intermediate hops are needed. Cisco v7 exposes `/test-results/{testId}/path-vis/agent/{agentId}/round/{roundId}`; this route requires `testId`, `agentId`, and `roundId`, and its response schema includes hop arrays. Cisco documents `roundId` and path `startTime`/`endTime` as epoch **seconds**, `systemMetrics.startTimeMs`/`endTimeMs` as epoch **milliseconds**, and `date` as UTC ISO date-time. For a precise test-result date range, Cisco's v7 API accepts `startDate` and `endDate` with complete UTC time in ISO 8601 form; don't substitute epoch values unless the endpoint schema specifies them. Do not convert or reinterpret result fields beyond documented units. [Path summary/detail API](https://developer.cisco.com/docs/thousandeyes/get-path-visualization-test-results-by-agent-and-round/) · [Endpoint path detail API](https://developer.cisco.com/docs/thousandeyes/retrieve-path-visualization-network-dynamic-test-results-details/) · [Path date-range API](https://developer.cisco.com/docs/thousandeyes/v7/get-network-test-results/)

## API rate, schedule, and retention

The current ThousandEyes v7 API documentation sets a default organization limit of **240 requests per rolling 60 seconds per organization**. Responses can include `X-Organization-Rate-Limit-Limit`, `X-Organization-Rate-Limit-Remaining`, and `X-Organization-Rate-Limit-Reset`; reset is a UTC epoch timestamp. On 429, Cisco says wait until the applicable reset header before retrying. These limits are subject to change. [ThousandEyes v7 rate limits](https://developer.cisco.com/docs/thousandeyes/v7/rate-limits/)

The 0.9.0 static client configures three generic retries with `backoff_factor=60` for 429 and 500–599 responses and does not read the `X-Organization-Rate-Limit-*` headers or calculate a delay from the reset timestamp (`bin/thousandeyes_client.py`). It also configures GET, POST, PUT, and DELETE as retryable methods. This is not an implementation of Cisco's rate-aware wait instruction. Event and path pagination can add requests; the organization limit is shared with other API callers.

The event input code deliberately sets its API `endDate` to **now minus eight minutes**, with the comment that CEA events can take up to eight minutes after `startDate` to become queryable. It persists a checkpoint and resumes from the previous `last_run`. First-run interval defaults conflict in the package: `README/inputs.conf.spec` says event default 300 seconds, while `default/inputs.conf` sets the event stanza to 3600 seconds. The static path-poll interval is 300 seconds in both files; it applies to Path Visualization polling, not the pushed OTel metrics cadence. Cisco's UI guide exposes an event interval but does not resolve the 300/3600 discrepancy. Set and read back the intended interval explicitly.

Cisco's retention/accessibility guide reports these API boundaries:

| Data | ThousandEyes accessibility limit |
| --- | --- |
| General Network and App Synthetics API test data | 90 days |
| Detailed Page Load, BGP, detailed Web Transaction, and detailed Path Visualization per-hop data | 30 days |
| Endpoint Experience API data | 30 days |
| Event Detection customer-facing API data | 90 days; UI history is 31 days (14 days for trial organizations) |
| Network & App Synthetics alert history | 90 days |
| Activity log | 13 months in the retention guide |

The separate “Working with the Activity Log” page says two years, which conflicts with the data accessibility guide's 13 months. Treat the API-accessible activity-log recovery window as unresolved without clarification from Cisco. Splunk index retention is configured separately; it cannot recover source data once ThousandEyes API retention has elapsed. [ThousandEyes data accessibility](https://docs.thousandeyes.com/product-documentation/user-management/user-activity/how-long-is-data-accessible) · [Activity log guide (conflicting 2-year statement)](https://docs.thousandeyes.com/product-documentation/user-management/user-activity/working-with-the-activity-log)

## HEC event timestamp and payload evidence limits

The app package sets `DATETIME_CONFIG = CURRENT` for its ThousandEyes sourcetypes in `default/props.conf`; Splunk describes `CURRENT` as assigning current system time at event merge and disabling timestamp extraction from event text. Separately, Splunk's HEC event format allows optional outer metadata including `time`, defined as the event timestamp, and accepts epoch seconds, milliseconds, microseconds, or nanoseconds. Cisco's app guide/package contains no captured ThousandEyes HEC request envelope demonstrating whether it supplies outer `time`, nor the exact JSON event body delivered by the current producer. These docs alone do not establish the final `_time` for this integration. Require a staged readback that preserves a redacted example of the HEC envelope and compares HEC `time`, event fields, and indexed `_time`; do not build a typed time contract from `DATETIME_CONFIG` or the OTel protobuf example alone. [Splunk HEC event format](https://help.splunk.com/en/splunk-enterprise/get-started/get-data-in/10.6/get-data-with-http-event-collector/format-events-for-http-event-collector) · [Splunk `props.conf` timestamp configuration](https://help.splunk.com/en/splunk-enterprise/administer/admin-manual/10.6/configuration-file-reference/10.6.0-configuration-file-reference/props.conf)

Cisco's direct OTel data-model examples are OTel structure examples (for example `timeUnixNano`, metric name/unit, point value and attributes), not examples of the app's actual Splunk HEC JSON serialization. The separate direct OTel guide documents a metrics endpoint and `mstats`; the Cisco app guide directs the app's metrics stream to `/services/collector/event` and an events index. Producer flattening, actual wrapper `time`, source/host overrides, and account-ID equivalence therefore remain readback requirements rather than assumed schema facts.
