# ThousandEyes Capabilities and Schema Evidence

This matrix is based on the user-supplied Cisco ThousandEyes App for Splunk 0.9.0 archive, its shipped `default/` configuration and `bin/` source, and current Cisco/ThousandEyes documentation. It distinguishes what the app configures from platform capabilities that the app does not select. No vendor code was run and no production data was collected.

### Metric families and producer units

The current official OTel v2 metric reference defines the following families and units. A metric name in the table is a platform capability; actual emission depends on the test's enabled layers and the app's selected tests.

| Test family | OTel metrics | Key dimensions | Units documented by ThousandEyes |
| --- | --- | --- | --- |
| Agent-to-server / agent-to-agent | `network.latency`, `network.loss`, `network.jitter` | source/target agent; server address/port; transport; I/O direction | seconds; percent; milliseconds |
| BGP | `bgp.path_changes.count`, `bgp.reachability`, `bgp.updates.count` | prefix, AS path, monitor ID/name/location | count; percent; count |
| HTTP server | `http.server.request.availability`, `http.server.throughput`, `http.client.request.duration` | server, port, URL scheme, HTTP method/status, error, DNS question | percent; bytes/second; seconds |
| Page load | `web.page_load.duration`, `web.page_load.completion` | server, port, error | seconds; percent |
| Web transaction | `web.transaction.duration`, `web.transaction.errors.count`, `web.transaction.completion` | marker/error | seconds; count; percent |
| API | `api.duration`, `api.completion`; per step `api.step.duration`, `api.step.completion` | step, server, port, scheme, method, DNS question, error | seconds; percent |
| DNS server / trace / DNSSEC | `dns.lookup.availability`, `dns.lookup.duration`, `dns.lookup.validity` | `dns.question.name`, error | percent; seconds; percent |
| FTP server | `ftp.server.request.availability`, `ftp.client.request.duration`, `ftp.server.throughput` | server, command, scheme, port, status, error | percent; seconds; bytes/second |
| SIP server | `sip.server.request.availability`, `sip.client.request.duration`, `sip.client.request.total_time` | server, port, response status, error | percent; seconds; seconds |
| RTP / voice | `rtp.client.request.mos`, `.loss`, `.discards`, `.duration`, `.pdv` | target agent and error | score; percent; percent; seconds; the official table duplicates a duration label on `.pdv`, so verify the exact metric output and unit before using packet-delay variation |
| Endpoint | scheduled/dynamic agent-to-server and scheduled HTTP server; platform additionally documents local network | endpoint agent/network profiles; local-network details include DNS, link, Wi-Fi/cellular, CPU/memory/battery | mixed per metric, see official OTel reference | 0.9.0 app filters out `local-network`; do not model it as package-collected data |

The app's data model uses a partial projection, not the full OTel v2 schema. Examples of OTel dimensions or metrics not declared in `default/data/models/Cisco_ThousandEyes.json` include `network.prefix`, `network.as.path`, target-agent location/geography, API step, and several endpoint local-network measurements. Raw JSON may retain attributes that the app model does not list, but the model is not evidence that each raw event contains them.

Cisco's metric reference lists metric names, values' units/types, descriptions, and resource/test attributes, but does not document the exact exported datapoint JSON keys or aggregation temporality. The package's `metric_name:<name>` fields are search-time expectations; the actual HEC event's metric value and timestamp paths still require sanitized readback. Do not assume `time_unix_nano`, `value`, `metric_name`, or any aggregation mode as verified producer fields solely from this app package.

## Package sourcetypes, source, index, and host

| Input | Source | Sourcetype | Index behavior in package |
| --- | --- | --- | --- |
| Metrics stream | Explicit `cisco:thousandeyes:stream` | `cisco:thousandeyes:metric` | User-selected test index in `exporterConfig.splunkHec.index` |
| Path visualization | No `source` assigned by modular-input event writer | `cisco:thousandeyes:path-vis` | Configured input index (the separate path index) |
| Trace stream | Explicit `cisco:thousandeyes:stream` | `cisco:thousandeyes:trace` | User-selected test index in HEC stream config |
| Event API | No `source` assigned by modular-input event writer | `cisco:thousandeyes:event` from input stanza | Configured input index |
| Activity stream | Explicit `cisco:thousandeyes:stream` | `cisco:thousandeyes:activity` | User-selected activity index in HEC stream config |
| Alert webhook | Explicit `cisco:thousandeyes:webhook` | `cisco:thousandeyes:alerts` | Selected alert index in webhook template |

All six sourcetype stanzas in `default/props.conf` say `DATETIME_CONFIG=CURRENT` and `KV_MODE=json`. The metrics/trace/activity inputs use OTel stream payloads with explicit HEC source/type/index. The alert template supplies source/type/index. For event/path, `smi.Event` receives a stanza and body; path also receives a sourcetype. The package does not set `host` for any family and does not explicitly set event/path `source`. Do not substitute Splunk host for a ThousandEyes source agent. Confirm event/path default source and any HEC host value by Splunk readback rather than guessing.

The package's `props.conf` aliases are convenience fields, not the stable raw schema. Examples:

- Metric: `server.address`→`dest`/`target`, `server.port`→`dest_port`, `http.request.method`→`http_method`, HTTP status→`status`, `network.transport`→`transport`, `dns.question.name`→`query`, plus a `response_time` evaluation multiplying client durations by 1,000.
- Trace: `thousandeyes.*` aliases into test/account/agent names, `name`→`span_name`, `kind`→`span_kind`, HTTP method/status and URL into older dashboard names; duration is derived from span nanoseconds.
- Path: `sourceIp`/`serverIp`→`src_ip`/`dest_ip`, `server`→`dest`, embedded response time and hop count aliases, plus endpoint network profile aliases.
- Activity: `thousandeyes.account.id`→`aid`; user, resources, and event fields gain app-friendly aliases.
- Alert: nested alert and top-level webhook fields map to app aliases such as `alertId`, `accountId`, `testName`, `severity`, and `ruleId`.

Raw keys and the source family must be retained alongside derived aliases. The model types some IDs differently from the OTel spec (for example, account/source-agent ID are numeric in the app metrics object but strings in OTel documentation); avoid irreversible casting.

## Account-group and path semantics

ThousandEyes API v7 defines `aid` as a unique account-group identifier obtained from `/account-groups`. The OTel v2 reference names `thousandeyes.account.id` and describes it as an account ID, without a direct normative statement that it equals `aid`. The Splunk app's own dashboards rename `thousandeyes.account.id` to `aid` and query the app's `thousandeyes_account_group` lookup. For correlation, retain both native values and record the mapping evidence (e.g. matching `/account-groups` row or sanitized live event); also retain alert `orgId` to avoid collapsing organization scope.

Cisco's current path API schemas provide distinct identity/time contracts:

- [CEA path result model](https://developer.cisco.com/docs/thousandeyes/pathvistestresult/): result fields include `date` as UTC ISO date-time, `roundId` as epoch seconds at the start of the round, `agent.agentId`, source/target IP details, and path summary values. The model does not list result `aid` or `testId`; the API call is scoped by query `aid` and path test ID.
- [Endpoint dynamic path results](https://developer.cisco.com/docs/thousandeyes/retrieve-path-visualization-network-dynamic-test-results/) and [scheduled path results](https://developer.cisco.com/docs/thousandeyes/retrieve-path-visualization-network-scheduled-test-results/): result objects include `aid`, `testId`, `agentId`, `roundId` (epoch seconds), target server, source/network profile, and path trace data. The per-hop result-details endpoints separately document hop `responseTime` in milliseconds.

The package's own source proves the CEA path identity gap. `test_metrics_stream_input.py` passes the selected `test_id` and account-group ID to `get_path_info` (lines 187–192); `thousandeyes_client.py` sends `aid` as request query context and the test ID in the endpoint path (lines 493–520); `test_metrics_stream_input.py` then serializes each `path` unchanged, with only stanza and sourcetype set (lines 332–338). Cisco's CEA result schema does not repeat either identity. For CEA path normalization, an external export adapter is therefore the required bridge: attach the configured request `aid` and selected test ID to each unchanged result, preserving native fields. The adapter may be an optional deployment component, but CEA path records cannot be admitted as typed account/test records without it or an adequate received native payload. This does not require installing or scheduling a new input in the Cisco Splunk package.

Path admission must use the explicit account/test identity emitted by that adapter or an administrator-attested exact source/index mapping. Never join path data by `host` or arbitrary IP/name coincidence. Keep `roundId` and `date` distinct. Cisco's CEA model defines `startTime` and `endTime` as epoch seconds for the round; the packaged `EVAL-duration=endTime-startTime` therefore computes seconds when both fields are present. Endpoint result summaries document `roundId` in epoch seconds; do not substitute nested endpoint `systemMetrics.startTimeMs`/`endTimeMs` (milliseconds for the metrics interval) for path round times.

## Event, alert, and activity boundaries

- **Detected events:** `event_input.py` calls `/v7/events` with account group and date bounds. It delays the query end by eight minutes, checkpoints `last_run`, follows pagination links, and adds `aid`. Its default input stanza interval is 3,600 seconds, while `README/inputs.conf.spec` says 300 seconds; use the configured value from Splunk, not either default as runtime fact.
- **Alerts:** `THOUSANDEYES_WEBHOOK_PAYLOAD_TEMPLATE` is the HEC contract. `accountId` is copied from `alert.rule.account.id`; `orgId` is separate. Test identity is present only inside the template's conditional test block. The setup path creates/updates webhook operations/connectors and edits alert rules; treat it as an explicit ThousandEyes configuration change.
- **Activity:** package constants select OTel `signal=log`, `dataModelVersion=v2`. The official model identifies activity logs with resource account/stream attributes and actor user attributes. The shipped `activity_logs_stream.py` does not poll the API despite an API activity URL constant in the client.

## Sanitized fixture requirements

Use representative, sanitized Splunk readbacks for all six families before freezing normalization. Include the outer HEC envelope where available, `_raw`, `host`, `source`, `sourcetype`, `index`, `_time`, and the exact configured input name/source. Preserve arrays and original numeric/string types.

1. **Metrics:** one OTel metric event for an HTTP/network metric and one for each needed test family. Keep metric name/value/unit/timestamp, account/test/source-agent attributes, test domain/type, and selected tags. Add BGP, endpoint and API samples only if those capabilities will be used; explicitly test whether `thousandeyes.account.id` matches the account-group `aid`.
2. **Path:** one CEA and one endpoint path result if both are used. Keep `date`/`roundId`, `aid`/`testId` when present, agent ID, target/source addresses, path trace array and response/hop units. The CEA sample is required to prove whether the deployed response carries account/test identifiers beyond the public schema.
3. **Traces:** a parent and child span for one page-load or transaction test. Add API per-step spans only after the app's API-trace support is confirmed from a sanitized stream sample or Cisco clarification. Preserve `trace_id`, `span_id`, parent ID, start/end nanoseconds, HTTP fields, account/test/source agent, and stream ID.
4. **Events:** one API event including account `aid`, event ID/type/severity/state and explicit start/end dates; preserve optional `affectedTargets[].affectedTestIds[]`/`affectedAgentIds[]` when returned and do not coerce multi-value IDs into a scalar.
5. **Alerts:** one triggered alert with a test and one supported alert without a test if that producer form occurs. Preserve `accountId`, `orgId`, alert/rule IDs, targets, severity and triggered/cleared values.
6. **Activity:** one audit record with actor and resource attributes; replace user name, email, address, account IDs, and resource names with synthetic values while preserving type and shape.

Remove tokens, authorization headers, actual URLs containing tenant/test IDs, account IDs, user names/emails/IP addresses, test targets, and customer tags. Do not invent placeholder values in production records; fixture placeholders must be clearly synthetic. A fixture proves parser behavior only, not that collection is complete.
