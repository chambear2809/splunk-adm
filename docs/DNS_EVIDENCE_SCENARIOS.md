# DNS evidence scenario guide

This guide describes how to interpret optional DNS evidence beside independently collected traffic. A DNS observation may provide query, response, resolver, answer, timing, and scoped-client context. A compatible DNS answer and traffic observation are supporting evidence only: they do not establish that a particular application call, process, or connection was caused by that lookup.

The scenarios below are operator interpretation boundaries, not claims that these environments were exercised. Adapter fixtures are synthetic and unqualified. There are no supplied genuine Stream DNS or Hubble DNS feeds, and no production topology or runtime example is qualified; see [DNS evidence qualification](DNS_EVIDENCE_QUALIFICATION.md).

## Source relationship limits

The Stream adapter retains the vendor-defined `host_addr` and `ttl` lists for inspection, but list position does not prove which TTL belongs to which address. Those lists alone do not produce associated answer records. A structured RR variant can support candidate address context only when the selected schema qualifies it, the RR is in the answer section, its owner matches the normalized question, its type matches the query, and each relevant answer has a usable TTL. An oversized reported list or missing response-end time suppresses association; `_time` alone is not a response-time basis. `response_time` is latency, not an event timestamp.

The Hubble adapter preserves its actual request/response endpoint direction and keeps scalar TTL as RRset context. Its unordered `ips` and CNAME collections lack per-record owner and section relationships, so they remain reported context and do not become answer records or synthesized alias chains. A `DROPPED` or `ERROR` verdict is retained only for a qualified schema. A schema flag is configuration, not proof that a deployed producer matches the profile; source qualification requires a representative sanitized event and recorded producer/exporter versions.

For either source, temporal correlation requires a qualified successful answer relationship, a selected scoped client, known compatible clock uncertainty, and a traffic observation inside the conservative answer-validity interval. The result says that observations are compatible; it does not claim a causal lookup-to-connection link. An unknown client owner can retain scoped-IP context without naming a workload. A known conflicting or reused owner prevents workload attribution.

## Test coverage and remaining evidence

Current adapter tests exercise normalization boundaries using explicitly synthetic fixtures: actual Stream field names/list behavior, Hubble's nested envelope and request/response direction, answer owner/section checks, missing and invalid TTL handling, CNAME non-expansion, timestamp basis, scope and ownership boundaries, duplicate exports, raw-byte limits, and explicit policy context. Endpoint tests exercise contract validation, scoped tuple handling, result caps, and configuration rechecks with synthetic rows.

These tests do not establish collector coverage, deployed schema compatibility, original-client visibility, clock synchronization, resolver behavior, topology-specific semantics, distributed Splunk behavior, or production capacity. There are no genuine sanitized DNS runtime examples for either source in this repository. Operators must qualify those facts for their own feed before enabling answer association; until then, treat DNS output as inspectable context only.
