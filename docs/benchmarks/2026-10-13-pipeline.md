## Scheduler: timing verified; recovery not yet qualified

`python3 tools/scheduler_pipeline.py --reset-lab`

The real schedules exposed invalid rollup rounding syntax: `@5m` did not
enforce the intended closed window. The shipped bounds now use `-10m@m`
through `-5m@m`, aligned by the five-minute cron. Splunk's parser regression
passed, and two subsequent real scheduled runs each collected exactly six
baseline flow records while leaving the next batch unprocessed before its
own eligible window.

An initial recovery attempt exposed a harness error: `status=continued`
startup deferrals were treated as terminal failures. They are now retained
as diagnostics while the harness waits for successful missed-slot runs.
Deferrals cannot certify catch-up; skips and failures still fail the run.

The next attempt was interrupted by shared-lab activity. Another process
restarted the container during the deliberate outage and installed the app;
the harness failed because its target schedules were no longer enabled.
[Incomplete scheduler report](2026-10-13-scheduler-incomplete.json) preserves
that result. No downtime-recovery success is claimed. A worktree separates
files but does not provide a separate Docker lab.

The scope-fixture setup was also corrected to write JSON records and verify
the stored observer mappings; escaped multiline CSV had silently produced an
empty lookup. See [benchmark qualification](../BENCHMARKS.md).
